ARIA Mistakes Demo Page

For demonstration only. Every example below contains an intentional ARIA mistake. Inspect with the accessibility tree and a screen reader.

Mistake #1: <div role="button"> with no keyboard support

Looks like a button. Acts like a button for mouse users. Completely invisible to keyboard users.

Submit Order

What's wrong: No tabindex, no Enter/Space key handler. Keyboard users can't reach it or activate it. Should just be a <button>.

Mistake #2: Redundant ARIA roles

Home | About |

What's wrong: <nav> already has the navigation role. <a> already has the link role. <button> already has the button role. This adds noise to the accessibility tree and can cause double-announcements in some screen readers.

Mistake #3: Icon-only button with no accessible name

What's wrong: Screen readers announce these as "button" with no context. Sighted users see a trash can, gear, and magnifying glass. Add aria-label="Delete", etc.

Mistake #4: Static aria-expanded that never updates

ARIA stands for Accessible Rich Internet Applications...

What's wrong: The button toggles the panel visually, but aria-expanded is hardcoded to "false" and never changes. Screen reader users always hear "collapsed" — even when it's open.

Mistake #5: aria-label that contradicts visible text

What's wrong: Sighted users see "Learn More." Screen reader users hear something completely different. Voice control users who say "click Learn More" can't activate it because the accessible name doesn't match. Visible text should be the accessible name.

Mistake #6: role="menu" used for site navigation

  • Home
  • Products
  • Pricing
  • About

What's wrong: ARIA menu is for application menus (like a right-click menu) and requires arrow-key navigation, not Tab. Screen reader users hear "menu" and expect that behavior. Site navigation should just be <nav> with links.

Mistake #7: aria-hidden="true" on a focusable element

Read our privacy policy before continuing.

What's wrong: Keyboard users can Tab to it, but screen reader users hear nothing when they land on it. Creates a "ghost" focusable element. Either remove aria-hidden or remove focusability — and really, just use an <a>.

Mistake #8: Form inputs labeled with aria-label when visible labels exist

What's wrong: The visible <label> is already correctly associated, but aria-label overrides it. Screen reader users hear "Enter your name here" instead of "Full Name." Drop the aria-label.

Mistake #9: Custom dialog with no dialog semantics

Are you sure you want to delete this item?

This action cannot be undone.

What's wrong: Looks like a dialog. Behaves like a dialog visually. But it has no role="dialog", no aria-modal="true", no aria-labelledby, no focus trap, no focus return when closed, no Escape key handler. Screen reader users have no idea a modal opened — focus stays on the page behind it. Use the native <dialog> element instead, which handles all of this.

Mistake #10: Heading role applied to a non-heading

What's wrong: Changing native semantics. The element is now both a button and a heading, which is confusing for assistive tech and inconsistent across screen readers. If it's a heading, use <h2>. If it's a button, use <button>.
